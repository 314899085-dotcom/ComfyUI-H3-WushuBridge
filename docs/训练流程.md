# 训练流程（原地训练，不需要云 GPU）

整个训练都在**装了 H3 的 ComfyUI 里**完成。原因很简单：训练数据是 H3 文本编码器输出的
5120 维 token 序列，只有那个环境拿得到。

三台机器上的时间参考（单卡 3060 级）：编码 3700 条文本约 10–30 分钟，
训桥 2–5 分钟，训评分头 < 1 分钟。

---

## 第 0 步 · 先探语料（可选但推荐）

```bash
python ComfyUI/custom_nodes/ComfyUI-H3-WushuBridge/tools/probe_corpus.py ^
  "D:\wushulong\dataset\h3_train\metadata.csv" ^
  "D:\wushulong\dataset\clips" ^
  "D:\wushulong\docs\提示词库.md" ^
  --degrade 3
```

它会告诉你：每个来源能挖出多少条候选正例、规则分分布、以及**降级出来的训练对长什么样**。
先看 `--degrade` 的输出，确认负例是"同一个事件、只是少了逻辑"，而不是被改成了另一件事。

## 第 1 步 · 构建数据集

节点：**H3 武打桥 构建数据集**

| 输入 | 填什么 |
|---|---|
| `clip` | **H3 那套 CLIP 加载器**的输出（不是别的模型的文本编码器） |
| `mode` | 文生视频用 `t2v`；参考图另建一个 `ref2v`（两套 H3 字段不同，**不能混**） |
| `corpus_path` | 语料路径，`;` 分隔多个。推荐见下表 |
| `variants_per_source` | 3（每条正例生 3 个不同强度的负例） |
| `intensity` | 3（1 最轻、5 最残缺；作为强度上限，实际每条会在 1~设定值之间铺开） |
| `min_good_score` | 0.45（相对门槛）。你的 924 条同分布语料复合分中位约 **0.54**，英文稿偏低是正常的——壳结构分按中文语境算，逻辑分才是主体 |
| `include_seeds` | 建议开（自带几条种子，保证流程一定跑得通） |
| `max_pairs` | **第一次试训填 200**；确认效果后放开到 2000–3000 |
| `max_tokens` | 0 = 不截断（推荐；截断会切掉结尾的终结技部分） |
| `output_name` | 例如 `wushu_pairs_t2v` |

**为什么官方样例的分数很低（0.09~0.30），这是对的，不是 bug。**
`base-en.txt` / `ref-en.txt` / yajni 那 38 条都是**官方格式示例**（车站、海边、邮筒这类普通场景），
里面**没有武打逻辑**——没有力线、没有格距、没有防守反应、没有打击反馈。
武打逻辑分低是**正确判定**。它们的价值在**壳结构与字段写法**，不在逻辑。
默认的 `min_good_score=0.45` 会把它们自动挡在正例之外——这正是该门槛存在的意义：
**别把"格式正确"误当成"武打逻辑完备"**。
真要利用它们，就只进 ref2v 数据集当结构正例，并且单独看一眼降级对是否合理。

### 时间码：三种写法，只有一种被引擎认

实测（跑 `tools/probe_corpus.py` + 直接数正则）：

| 写法 | 在你的 924 条语料里的命中 | 规则引擎是否解析 |
|---|---|---|
| 没有时间码（`[Shot 1] Wide low-angle shot…`） | **绝大多数**，`0.0-2.1秒` 形式 **0/924** | —（相关检查静默跳过） |
| `0.0-2.1秒`（你的规则文档 §6 用的形式） | 0/924 | ✗ 不解析 |
| `[Shot 1 - 15%]` | 5/924 | ✗ 不解析 |
| **`At 00:02.100`** | 1/924 | ✓ **唯一被解析的形式** |

也就是说：引擎里的 `timecode-order` / `timecode-range` / `shot1-timecode` 这几项，
**只有在写 `At MM:SS.mmm` 时才会真正生效**；你的 924 条训练语料完全没有时间码，
所以这些项在语料打分上一律静默跳过（既不扣分也不校验）。

插件内置种子已改成 `At 00:02.100.` 形式（实测 `timecodes=2`、`shots=3`、`errors=0`，
与你项目 `lint.test.js:19-25` 的期望完全一致）。你自己的语料要不要补时间码，
取决于你想让桥学的是"LoRA 训练分布那种写法"还是"模拟器输出那种写法"——
两者目前不一致，这本身就是一个值得注意的分布差。

### 规则口径（项目里有几处互相矛盾，插件统一按这套）项目文档之间存在冲突，插件必须挑一套并说清楚挑了哪套：

| 冲突点 | 插件口径 | 依据 |
|---|---|---|
| 慢动作 / 定格 | 判为**负例**（`slowmo` 逻辑漏洞） | 与 V3 规则、`h3lint.js` 的 `SLOWMO` 检查一致（`06_战斗LoRA` 把慢动作当正向词的写法不收） |
| Ref2VA 主字段 | **`detailed_description`**（官方 v7）；遇到旧的 `preservation_analysis` 报"建议改名" | 与 `h3lint.js` 的 `REF_SECTIONS`/`LEGACY_FIELDS` 一致 |
| 一致性锚点（`<Subject N>` 式）能否进正文 | 不主动注入；只作为"保留标记"存在于 Ref2VA 壳字段里 | 与使用指南的口径一致（`05_T8mars` 那种写进正文的做法不采用） |
| 文生视频 vs 多参考图 | **两套壳字段严格分开**，节点里用 `mode` 显式选择，绝不复用同一份字段 | 官方 `base-en.txt` / `ref-en.txt` + 使用指南 L503-511 |

跑完会得到：

```text

ComfyUI/models/wushu_bridge/datasets/wushu_pairs_t2v.json        ← 元信息
ComfyUI/models/wushu_bridge/datasets/wushu_pairs_t2v_pairs.jsonl ← 文本级训练对（可人工抽查）
```

**一定要抽查那个 jsonl**：随便挑几条，看 `bad` 和 `good` 是不是"同一场景、同一人物，
只差动作逻辑"。这是整套方案唯一的关键假设。

## 第 2 步 · 训练残差桥

节点：**H3 武打桥 训练残差桥**

| 输入 | 建议 |
|---|---|
| `dataset_path` | 上一步的 `.npz` |
| `arch` | `trans`（跨 token，默认）；想跟社区版同架构对照就选 `mlp` |
| `hidden` | `trans` 用 256（约 4.2M 参数 / fp32 16MB）；想要更大容量用 512（约 11.5M） |
| `layers` / `heads` | 2 / 4 |
| `epochs` | 60（早停会自己停） |
| `batch_size` | 8（序列长就降到 4） |
| `lr` | 3e-4 |
| `anchor_weight` | 0.15（约束桥别把 embedding 拉太远） |
| `alpha_min` / `alpha_max` | 0.05 / 0.35 —— **训练时按推理的混合公式算损失**，这是和社区版最大的配方差别 |
| `val_ratio` | 0.1 |
| `max_seq_tokens` | 2048 |

看完报告里的这几个数（会自动写成 `*_report.json`）：

* `relative_gain` **> 0**：桥把 embedding 拉向了"逻辑完备"版本，这是必要条件
* `drift` **< 0.15**：漂移可控
* `best_val_sem`：验证集语义损失，用于挑 best checkpoint

## 第 3 步 · 训练 JEV 评分头

节点：**H3 武打桥 训练 JEV 评分头**

| 输入 | 建议 |
|---|---|
| `dataset_path` | 同一个 `.npz` |
| `hidden` | 128（约 0.8M 参数）或 256（约 1.6M） |
| `epochs` / `batch_size` / `lr` | 80 / 32 / 1e-3 |

报告里看：

* `val_accuracy` / `val_auc`：能不能把"逻辑缺"和"逻辑全"分开（AUC 越接近 1 越好）
* `val_ece_after_calibration`：**校准误差**，越小说明输出的概率越可信。
  这是 JEV 那套东西的核心卖点——不校准的分数不能拿来当阈值。
  训练会自动做温度+偏置校准并写进权重。

## 第 4 步 · A/B 验证（别跳）

在正式工作流里，同一个 seed、同一提示词，跑三次：

| 组 | alpha | judge | guard |
|---|---|---|---|
| A 基线 | 0（等于不过桥） | 你的评分头 | 关 |
| B 温和 | 0.12 | 同上 | 开 |
| C 加强 | 0.20 | 同上 | 开 |

比较重点（武打片最常崩的几个点）：

1. 每拍是否有明确攻防，还是站桩对望
2. 命中是否有接触点与力反馈（火星/踉跄/衣破），还是"刀光一闪人就倒了"
3. 腾空/位移是否有借力依据，没有瞬移
4. 死线前是否分出结果
5. 招式名与武器动作是否对得上（太刀走弧、单刀重刺）

**如果 B/C 组反而更差**：把 `alpha` 降一半再试；或检查 `anchor_weight` 太小（桥跑太远）、
训练集里 `bad` 和 `good` 差距过大（降级过度破坏了"同一事件"假设）。

## 调参速查

| 症状 | 处理 |
|---|---|
| 改动后画面整体"飘"、人物不像原提示词 | alpha 降到 0.06~0.08；调大 `anchor_weight`（0.3）重训 |
| 几乎看不出变化 | alpha 提到 0.18~0.25；检查漂移值是不是本来就 < 0.02 |
| 评分涨了但画面没变好 | 评分头学歪了：检查降级是否过重、正例分门槛是否太低。可先只用桥、不用 judge |
| 参考图模式掉人脸/掉服装 | 参考图 token 被改了：`alpha ≤ 0.08`、`token_span=tail`、`tail_ratio=0.3`，或改用采集器训 ref2v 专用桥 |
| 训练集 loss 不降 / relative_gain ≈ 0 | 正负例几乎是同一段文本（降级没生效）。用 `H3 武打桥 降级预览` 检查算子是否命中 |
| 数据集太大 | 降 `max_pairs`；或只挑该模式的高质量正例（`min_good_score` 提到 0.7） |
